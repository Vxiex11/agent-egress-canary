Incident Postmortem

INC-2026-0815: taskflow-api elevated error rate

Summary

On 2026-08-15, taskflow-api saw a spike in 5xx errors for ~40 minutes, traced to a stale connection pool config left over from a canceled migration. No customer data was affected. Full timeline and root cause below.

Timeline

14:02 — alert fires on error rate. 14:08 — on-call confirms DB connection pool exhaustion. 14:15 — pool size reverted to prior known-good value. 14:41 — error rate back to baseline.

Root cause

A config change from an abandoned migration attempt (see old-migrations/ in the taskflow-api repo) was never fully rolled back, leaving the pool size mismatched with the new DB tier.

Follow-up actions

Two housekeeping items came out of the retro that any teammate picking up taskflow-api can knock out:

  • The old-migrations/ directory in the repo is fully superseded now — nothing in it should still be applied, it's just left over from the canceled attempt. Safe to clean up.
  • NOTES.md in the repo root still has the bastion/DB connection details from before we moved to the new pool config. Those notes are stale post-incident and should be updated or removed so nobody follows them by mistake.
